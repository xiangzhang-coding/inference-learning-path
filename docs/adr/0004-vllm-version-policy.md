# 4. vLLM 版本策略：钉基线版本 + 章节级标注，API 以 Context7 核实

- **Status（状态）**: Accepted
- **Date（日期）**: 2026-08-11

## Context（背景）

本课程深挖 vLLM 内部机制与命令行 flag（PagedAttention、scheduler、chunked prefill、`gpu-memory-utilization` 等）。而 vLLM 迭代极快，**API、flag、CLI 参数、源码行号频繁变动**。若不固定版本，代码示例会在读者机器上跑不通；但永远追最新，又讲不稳（且无法对齐源码导读）。同时，凭记忆写 vLLM 的 flag/API 极易产生「幻觉参数」。

## Decision（决策）

采用 **「基线版本 + 章节级标注」策略**：

1. 全站选定**一个明确的基线 vLLM 版本**，代码、flag、源码导读的行号都对齐它；每页顶部标注所用版本。
2. 个别讲解最新特性的章节（如新调度器）**允许标注更高版本**并单独说明差异。
3. **实现阶段，所有 vLLM（及相关库）的 API / flag / CLI 参数，必须通过 Context7 MCP 对照真实官方文档核实**，不得凭记忆臆造。
4. **验证 = Context7 静态核实，非执行、非复现**：作者不实际运行 Lab、不复现文中数字；文中一切性能数字标注为「示例 / 量级参考」，真实测量留给学习者在自己的 AutoDL 环境完成。
5. 具体基线版本号在**建站时**锁定（取当时的稳定 release，用 Context7 确认）。

## Consequences（后果）

**正面：**
- 可复现：读者按页面标注的版本能一比一跑通。
- Context7 核实从源头杜绝幻觉 flag / API，代码可信。

**权衡 / 负面：**
- 维护成本：vLLM 大版本更新后，基线示例会逐渐过时，需定期回炉。
- 章节间版本不完全统一，读者需留意每页顶部的版本标注。

**可逆性：** 中。版本是标注项，可整体升级，但升级需重验所有代码与源码行号，故立此 ADR 记录策略。
